## 4. Milestone 3：把方案转成可验证的需求

### 4.1 推荐的 SRS 结构

1. 项目目的与范围：系统解决长期对话中的状态变化问题，写清必做与扩展边界。
2. 使用者与使用场景：导入数据、查看记忆、提出当前或历史问题、检查证据、导出记忆。
3. 数据与术语：Memory、实体、属性、时间、来源、RETAIN、UPDATE、SUPERSEDE、有效记忆。
4. 功能需求：按导入、抽取、查询、解析、回答、可视化、导出分组，每条有唯一编号。
5. 非功能需求：可追溯、可复现、失败处理、安全配置，以及经过测量后可执行的性能目标。
6. 外部接口与数据约束：JSON 格式、接口输入输出、字段校验、错误信息。
7. 验收与评测：测试场景、三项指标、两种对照、数据划分。
8. 需求追踪与未决事项：需求对应实现、测试、证据；记录尚未确定的问题。

篇幅限制确认后压缩正文，详细 Schema、测试表和追踪矩阵是否可放附件也应确认。上述结构是编写建议，课程未提供逐章模板。

### 4.2 功能需求建议表

| ID | 推荐需求 | 验收证据 |
|---|---|---|
| FR-01 | 导入课程指定对话并区分开发集、测试集 | 数据清单、导入结果、错误输入测试 |
| FR-02 | 从原始对话自动构建结构化 Memory，保存内容、时间和来源 | 导出 JSON 与来源核查 |
| FR-03 | 在 Web 中查看 Memory 及其原始证据 | 点击记忆可查看对应会话、轮次与文本 |
| FR-04 | 输入问题后，从所选对话完整历史自动检索候选记忆 | 候选 ID、排序、检索日志 |
| FR-05 | 判定相关记忆的保留、更新或替代关系 | 关系标签、前后记忆 ID、判定依据 |
| FR-06 | 根据问题和时间条件选择有效证据，保留历史记录 | 当前问题与历史问题返回不同的适用证据 |
| FR-07 | 基于有效证据回答，并关联来源 | 答案与证据对应；不足时明确表示无法确定 |
| FR-08 | Web 展示检索结果、关系和有效性解析 | 可重复的端到端演示和截图 |
| FR-09 | 导出统一 JSON，保持 ID 与来源字段稳定 | 导出可再次解析，来源没有丢失 |
| FR-10 | 运行项目方法及两个对照，输出三项评测结果 | 配置、逐题结果、汇总表 |

为每条需求补齐触发条件、输入、正常输出、异常情况和验收步骤。不要只写“系统支持智能检索”“算法准确率高”等无法判断是否完成的描述。

示例：FR-06 输入问题、可选 as_of 时间和候选记忆；系统输出有效记忆列表、关系及理由。历史记录保持可追溯。当时间证据不足时输出不确定状态，不直接按输入顺序判定最新。

### 4.3 时间与状态语义必须说清楚

- 区分“对话发生时间”和“事件发生时间”。例如 last Friday 需以对应会话时间解释，不能以系统今天解释。
- 定义“当前”的参照时间。推荐显式传入 as_of；未传入时使用所选对话的已知时间边界，并在界面显示。该默认行为是建议，需团队确定后写进 SRS。
- UPDATE：同一状态或过程继续演进，例如申请收养 → 通过面试。
- SUPERSEDE：针对某个问题与时间，新事实替代旧事实的回答适用性。旧事实仍是历史证据。
- RETAIN：相关事实仍适用，或新事实没有推翻它。较旧的事实并不天然无效。
- CONFLICT：证据支持互斥状态，且时间或上下文不足以消解时，保留来源并标记不确定。
- 不同属性不能随意相互替代。开网店与失去某份工作不能脱离查询范围直接作为全局互斥事实处理。
- 有效性是问题和时间条件下的判断。避免给每条 Memory 永久设置一个全局 active/inactive 标记后用于所有问题。

### 4.4 建议的数据契约

以下是接口讨论示例，不是课程强制字段集合，也不代表课程真实数据样本。

```json
{
  "memory_id": "example_mem_003",
  "conversation_id": "example_conv",
  "content": "The person passed the adoption agency interviews.",
  "entity": "ExamplePerson",
  "attribute": "adoption_status",
  "value": "interviews_passed",
  "session_time": "2023-10-22T09:55:00",
  "event_time": null,
  "time_expression": "last Friday",
  "source": {"session": 19, "turns": ["D19:1"]}
}
```

查询结果单独保存 query_id、as_of、retrieved_ids、relations、effective_ids、answer 和 evidence_ids。关系记录至少含前后 Memory ID、标签及依据。允许 event_time 未确定，不要为了填字段编造日期；一条记忆跨多个轮次时应保留多个来源。

## 5. Milestone 4：展示一个完整、可解释的可运行版本

### 5.1 最小闭环与模块边界

中期先让一个开发集案例完整运行，再扩展到多个问题。最终必须完成指定的全部课程数据；中期阶段可以明确报告当前覆盖情况和剩余工作。

| 模块 | 输入 → 输出 | 关键约束 |
|---|---|---|
| 导入与抽取 | 原始对话 → Memory JSON | 来源可追溯；失败记录可定位 |
| 索引与检索 | 问题、对话 ID → Top-K Memory | 按对话隔离；不能预先输入标准证据 |
| 状态解析 | 问题、时间、候选 Memory → 关系与有效证据 | 保留历史；处理时间与属性范围 |
| 回答 | 问题、有效证据 → 答案与来源 | 不将未知信息当作已知事实 |
| Web | 各阶段结果 → 可检查的界面 | 展示原文、关系、有效性与错误状态 |
| 评测 | QA、预测结果 → 指标与逐题记录 | 标准答案只用于评分 |

参考计划已有 React + ECharts 原型，若实际可用，继续沿用。后端、存储和检索实现优先选择团队熟悉的工具；不要因接近中期而全面换技术栈。抽取、关系判断和回答可以复用模型调用封装，但日志与输出要分别记录。

10 月 18 日前至少完成：导入或加载真实开发对话、构建记忆、输入问题、检索、解析、回答、Web 展示来源。随后重点处理模块契约、错误响应和数据一致性。

### 5.2 中期测试建议

| 场景 | 重点检查 |
|---|---|
| 单条明确事实 | 能检索并给出对应来源 |
| 收养等阶段演进 | 当前问题采用后续阶段，历史阶段仍可查看 |
| 带过去时间的问题 | 不用晚于查询时间的事实替代当时状态 |
| 不同人物、同类属性 | 不将不同人物的记忆串起来 |
| 不同属性并存 | 新增爱好不替代职业或家庭事实 |
| 无相关证据 | 明确无法确定，不给出无来源答案 |
| 时间无法解析 | 记录不确定性，不任意补日期 |
| 互斥信息 | 展示冲突及来源，解释是否能够消解 |
| JSON 导出 | 可解析、ID 唯一、必需字段与来源完整 |
| 服务失败 | 页面显示可理解的错误，能重试或恢复 |

推荐中期准备约 8–12 个固定回归案例，包含上述主要场景，并对自动抽取的记忆做人工抽查。案例数量是内部建议；测试需要验证实际行为，不能只检查页面是否打开。

分别记录错误来自抽取、检索、时间解析、关系判断还是回答。若检索没有召回正确证据，不能直接把后续失败全归为状态解析错误。

### 5.3 展示组织与演示顺序

若确认展示限 10 页，可采用以下结构；实际讲述时间按课堂安排缩放。

1. 问题与项目范围：长期对话的状态变化为什么会使回答出错。
2. 核心需求与当前完成范围：用需求编号对应已完成能力。
3. 数据与 Memory：显示真实原文、结构化结果和来源。
4. 系统设计：抽取、检索、解析、回答、Web 的数据流。
5. 关系与时间：解释 RETAIN、UPDATE、SUPERSEDE 和查询时间。
6. 实机演示：输入问题，检查候选、关系、有效证据和答案。
7. 对照案例：展示 Vector RAG 与动态解析的差异；标明是否为开发集示例。
8. 测试与初步结果：展示实际测试数量、通过情况和失败点。
9. 当前限制与后续工作：说明哪些指标或功能仍待最终验证。
10. M5 计划：剩余数据、对照实验、独立测试和报告时间。

建议准备一个成功案例和一个失败或不确定案例，让展示体现系统边界。备用材料包括本地已保存结果、截图或录屏；现场无法调用服务时说明使用的是预先运行结果，不能将缓存冒充实时运行。

## 6. Milestone 5：形成可信、可复现的最终结果

### 6.1 数据隔离和实验冻结

建立数据清单，保存对话 ID、开发/测试划分、文件版本及问题数量。开发阶段用 4 段开发对话调整抽取、K、提示词、规则和阈值；独立测试集的答案、标准证据、关系和有效 Memory 不进入系统输入或调参流程。

测试集完整历史对话可以用于自动构建记忆和检索，因为课程要求从完整历史中运行系统；禁止的是利用测试标准标注指导预测。正常系统输入只包括允许使用的原始对话、问题及其时间条件。

11 月 2 日建议冻结代码版本、模型、提示词、检索设置和评分口径。若最终测试发现程序错误，修复后记录版本、原因和重跑范围；不要反复依据测试答案调参后仍将结果称为独立测试。

### 6.2 三种方法怎样公平比较

| 方法 | 输入与处理 | 要控制的变量 |
|---|---|---|
| Full Text | 将完整对话作为回答上下文 | 相同 QA、回答模型与评分规则；记录上下文是否容纳全部历史 |
| Vector RAG | 从相同 Memory 中检索后直接回答 | 相同抽取结果、检索器、K、回答模型，不执行状态解析 |
| 项目方法 | 相同检索结果经动态解析后回答 | 保持检索与回答条件可比，显式记录解析增加的步骤 |

Full Text 若受模型上下文限制，必须报告限制与处理方式；不能把任意截断结果直接写成完整全文对照。先检查所选模型上下文容量和完整输入长度，再确定可比方案。

除课程三个指标外，可补充单次查询延迟、模型调用量或成本作为辅助结果。不要为了补充指标耽误必做评测。若进行消融，可先做“启用/禁用动态解析”的比较，避免同时改变多个因素导致无法解释差异。

### 6.3 指标定义与评分口径

优先使用课程提供的评分脚本和定义。没有提供时，应事先写明以下口径并向助教核实，而不是实验结束后选择最有利的算法。

- **QA F1**：说明答案规范化、分词、多参考答案和空答案处理；若自行采用 token-level F1，应注明实现。不能用主观“答案看起来正确”代替自动评分。
- **证据 Recall@K**：按原始证据轮次将返回 Memory 映射回 source，去重后计算命中比例，再按约定汇总。明确 K 数值、候选阶段还是有效证据阶段、无标准证据问题如何处理。为便于定位问题，建议分别报告检索候选与最终有效证据的召回。
- **动态更新判断准确率**：先确认评分单位是关系对、单条记忆有效性还是整道问题状态集合，并明确 UPDATE / SUPERSEDE 是否合并。若采用关系对分类，准确率为正确标签数除以参与评分的标注关系对数；额外提供混淆矩阵帮助识别多数类偏置。

Full Text、Vector RAG 通常不输出动态关系；其关系判断指标可标 N/A，不应杜撰分数。Full Text 的证据检索指标若没有独立检索或引用定位输出，也需说明不适用或按课程指定口径处理。

可使用标准证据做一个独立的“给定正确候选，解析是否正确”诊断实验，但必须标注为诊断或 oracle 实验，与端到端主结果分开；主结果依然要求自动从完整历史检索。

### 6.4 必须保留的实验材料

- 数据划分、各对话和 QA 数量、各方法使用的配置。
- 代码版本、模型名称与版本、提示词版本、K、随机性设置及运行时间。
- 每题候选 Memory、预测关系、有效 Memory、答案、引用、耗时与失败信息。
- 自动评分结果、汇总脚本或操作说明、失败案例分析。
- 若服务有随机性或波动，报告运行次数与波动；资源不足只跑一次时明确说明，不虚构稳定性结论。

建议把失败案例归为：抽取缺失、来源错误、检索漏召回、实体混淆、时间误解、错误替代、冲突处理、答案生成。每类选典型案例说明原因、影响与可行改进。

### 6.5 最终报告推荐结构

1. 问题与目标：联系长期对话状态变化，明确已实现范围。
2. 需求与约束：课程要求、用户场景、数据划分和需求追踪。
3. 设计与实现：Memory、检索、时间与关系解析、回答、Web。
4. 测试：正常、异常和回归场景，覆盖与剩余缺陷。
5. 实验设置：数据、三种方法、指标、模型、配置与公平性。
6. 结果与分析：真实汇总表、典型案例、误差来源；开发与测试分开。
7. 限制与后续工作：证据召回不足、时间不确定性、计算开销等实际限制。
8. 项目过程：两轮迭代、计划调整、版本管理与评审证据。
9. 运行与复现说明：环境配置、启动、导入、导出和评测步骤。

结果表可以先建模板，数值只在实验完成后填入。若项目方法某项没有提升，直接报告并分析原因；选取成功演示不能替代整体结果。

## 7. 工作组织与过程证据

无需按姓名分配，按模块明确一个直接责任角色和一个评审角色即可。规模较小的团队允许兼任，但关键结果应由另一人检查。

| 工作模块 | 核心交付 | 协作依赖 |
|---|---|---|
| 需求与文档 | SRS、追踪表、报告、展示 | 读取各模块实际接口、结果和限制 |
| 数据与抽取 | 数据清单、Schema、Memory JSON | 提供稳定 ID 和可追溯来源 |
| 检索与动态解析 | 查询链路、关系与时间判断 | 使用已冻结 Schema，输出可检查日志 |
| Web 与集成 | 证据查看、解析展示、演示 | 尽早使用模拟契约联调，再替换真实结果 |
| 测试与项目管理 | 回归、实验、过程归档、提交检查 | 各模块持续提供版本和失败信息 |

推荐目录（可按现有仓库调整）：

```text
docs/          SRS、设计、报告、展示源文件
src/           系统源代码
tests/         功能与回归测试
data/          数据清单、允许归档的数据与 Memory
evaluation/    配置、逐题预测、评分与汇总结果
process/       会议记录、评审意见、迭代计划、截图
README.md      环境、运行与复现说明
```

每个里程碑至少保留：第一轮产出、评审问题、第二轮修改、测试证据、提交版本。会议记录应含日期、议题、决定、行动项、截止时间和关联问题。不要事后编造会议、提交历史或已完成状态。

每个行动项写成可验收的产出，例如“实现来源跳转，3 个案例验证成功”，避免“继续完善前端”。任务建议控制在半天至一天可见成果，阻塞超过一天就明确原因并调整安排。

## 8. 进度不足时的取舍

| 风险 | 预警信号 | 建议处理 |
|---|---|---|
| 范围过大 | 中期前仍在同时开发图检索、压缩、多跳等功能 | 暂缓扩展，集中完成必做闭环 |
| 集成过晚 | 各模块单独可用但没有共同跑过一个问题 | 当天固定接口，用真实案例端到端联调 |
| 解析失真 | 总是选择最新记忆，不区分问题和属性 | 优先补历史查询、不同属性和冲突案例 |
| 数据泄漏 | 用标准证据筛选主流程候选，或看测试答案调规则 | 分离评分与推理输入，恢复独立评测流程 |
| 实验来不及 | 11 月初仍未运行任何对照 | 先完成三方法基本结果，再选择改进方向 |
| 展示不稳定 | 外部服务失败会让演示完全中断 | 准备可标识的缓存结果、录屏与错误反馈 |
| 过程证据不足 | 完成任务没有评审、测试或版本记录 | 从现在起同步归档，不事后补造 |

削减顺序建议：动画和视觉装饰 → 扩展功能 → 更多实验组合。结构化记忆、来源追溯、动态解析、Web、独立测试和两种对照属于课程核心，不宜作为缩减项。
